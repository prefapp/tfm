# OVH administrator credentials in OKMS; application users remain outside

The module manages OVHcloud's existing `avnadmin` account by declaring the provider's `ovh_cloud_project_database_user` resource with `name = "avnadmin"`. OVH maps that name to the cluster's pre-existing administrative account and the provider resets its password; it does not create an additional MySQL account. The generated username and password are published as JSON to a caller-selected OKMS path. The path is exposed as an output, but the password is not.

This exception does not extend to application users. OVHcloud API-created MySQL users receive administrator-equivalent grants, while least-privilege application users must be created with SQL and cannot be managed through the OVHcloud API. Managing those SQL accounts here would require a separately staged SQL connection whose endpoint and bootstrap credentials only exist after service creation. A future user-provisioning workflow can manage SQL accounts in a separately configured lifecycle. See [OVHcloud's MySQL user guidance](https://docs.ovhcloud.com/en/guides/public-cloud/databases/mysql-prepare-for-incoming-connections/#step-1-verify-your-users-and-password).

The password is sensitive in provider output and in the OKMS payload, but both the OVH provider resource and OKMS resource retain sensitive values in Terraform state. Consumers must protect and encrypt state and plan files. A non-null default for `admin_password_reset` ensures the provider resets the pre-existing admin password when first managing it; changing the trigger requests a new password and causes OKMS to publish a new secret version. Removing the user resource from Terraform state does not delete or disable the OVH-managed `avnadmin` account; deleting the OKMS secret removes the credential destination and may make the current password unavailable to consumers.
